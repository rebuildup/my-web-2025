## 観点 (5 things)

### 1. なぜ 259 PR が pile-up したか

`chore/sync-submodules-YYYYMMDDTHHMMSSZ` workflow は 15 分 cron で走り、 
`bun.lock` を refresh しないまま PR を作る設計だった (`.github/workflows/sync-submodules.yml` lines 119-125 旧版)。 
merge-safe でない PR が 1 日 20-30 件来ると人間の reviewer が認知破綻 → 全 PR 
0 merge / 0 close の最悪状態。 **feedback loop 欠如**: 「bot が PR を作る → 人間 
が review → merge or close」の連鎖が自動化されておらず、 bot 側に close 機構が無かった。

### 2. なぜ `fix/bun-pm2-deploy-bootstrap` が 1.5ヶ月 放置されたか

WIP=1 violation (該当 branch は main と乖離したまま誰も拾わなかった) + retro スキップ。 
前 sprint (2.1.x) では retro が run されず、 stale branch 検出 mechanism が無かった。 
**学習**: solo agile は retro を **必ず sprint close で** run する discipline が必要。

### 3. sync-submodules をどう再開するか

PR #393 の `agile-premises.md` で "release = `release-x-y-z` → main" を canonical 化したので、 
再開も **直接 main push** 案 (案 A) を推奨:
- submodule drift 検出 → 直接 `git push origin main` で gitlink 更新
- CI は main push で trigger、 PR review は人間の判断に委ねる
- 案 B (weekly cron + PR 1本/week) は次善
- 案 C (submodule 側 pull モデル) は submodule 側にも `PARENT_REPO_TOKEN` が必要で重い

### 4. AGENTS.md dispatcher 化は運用に乗ったか

✓ Yes. `docs/agent/agile-premises.md` が reference され (Issue #398 merge)、 
backlog Issue (#395, #396, #401) や housekeeping 経路で dispatcher が指す docs 群 
(`release-workflow.md` / `quality-security.md` / `parallel-orchestration.md`) を 
実際に読んだ。 dispatcher 化は lightweight で機能している。
